# Public Wall media and Free Claim UX

## Placement-based media

The stable public URL is `GET /public/placements/:placementId/autograph`. It works without authentication and is independent of Free Claim source or Wall claimability. The API checks that the Placement is active, its Wall is public (scheduled/live/paused/ended), it has an Autograph owned by its User, and the Autograph is `ready`. Placement and Wall rows are held with shared locks while this evidence is resolved, so archive cannot race the visibility check. Draft/archived Walls return a no-store 404 even when a previously known Placement ID is supplied. Previously cached public bytes retain the documented maximum 60-second lifetime. It calls the shared evidence verifier for the owner approval, exact uploaded cleaned Asset, and approved Moderation Decision. It also checks the cleaned Asset's PNG metadata. A focused service then reads the private cleaned object with a 10 MiB byte limit, checks its length and PNG signature, and returns `image/png`. It never reads or falls back to the original. The bucket remains private and the browser never sees storage keys or owner preview URLs.

Missing, ended, or inconsistent media returns public 404 with no internal reason. Evidence inconsistency, missing private object, other storage failure, and invalid object bytes are distinguishable in internal logs by Placement ID and reason only. Success responds with `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, and `Cache-Control: public, max-age=60`; failures use `no-store`. A fresh request after Placement completion fails. Previously cached public bytes may remain until the short cache lifetime expires.

`GET /walls/:id` joins active Placement, Autograph, approval, cleaned Asset, and moderation evidence in one query. It emits only a relative `mediaPath` when that evidence is consistent. Occupancy always follows active Placement, so unavailable media produces `occupied=true` and `mediaPath=null`. Missing storage is detected by the image endpoint; the page falls back to an unavailable state if the image fails. Wall JSON uses `Cache-Control: no-store` so manual refresh observes current occupancy. The Wall API does not download images or disclose User, Autograph, evidence, Asset, or storage identifiers.

## Owner selection and claim flow

Authenticated `GET /autographs?status=ready` returns up to 30 recent owner choices after evidence verification. A bounded 50-row candidate scan excludes inconsistent ready records. Each item contains ID, source, creation time, and moderation time; no storage metadata. The browser uses the existing owner-only preview endpoint for the selected Autograph. Signed preview URLs stay in component memory, are refreshed before expiry, and are never used for public Wall images.

The server renders initial public Wall data using `API_INTERNAL_URL`. The browser uses `API_PUBLIC_ORIGIN` for refresh, auth, preview, claim, and public media. The page works anonymously and offers the existing Google/Telegram login flow with a fixed `/walls/<id>` return path when an empty Slot is selected. Authenticated Users without ready Autographs are directed to `/autograph/create`. A User selects a ready Autograph, selects an empty Slot, sees the one-use warning and confirmation, then sends the existing Free Claim request. Both 201 and exact-retry 200 are success; the page refetches the Wall before displaying the new occupied Slot. `SLOT_OCCUPIED` refreshes without trying another Slot, `FREE_CLAIM_ALREADY_USED` disables further attempts, and `WALL_NOT_CLAIMABLE` refreshes and disables the flow. Manual Refresh provides a low-cost update path without push infrastructure.

Browser timing only controls presentation. PostgreSQL remains authoritative for Wall eligibility, Slot occupancy, and Autograph evidence. Scheduled, paused, and ended Walls remain readable without mutation controls; draft and archived Walls remain 404. Owner preview and API session requests use existing cookie auth and origin protection. Browser web/API origins must remain compatible with the existing SameSite cookie setup; local MinIO and production S3 need CORS for browser preview, but never public bucket access.
